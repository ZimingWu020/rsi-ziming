Where RSI Stands Today: AI Systems That Rewrite How They Work

2026.11.04 · 14 min

Talk of recursive self-improvement (RSI) often conjures a dramatic picture: an AI improves itself, grows stronger, then improves again, until capability accelerates in a runaway loop. Recent research is more concrete. What these systems usually modify is not the large model itself, but the code around it—how to read materials, call tools, store experience, and recover from failure.

That layer of code is often called the harness: the agent’s runtime framework. With the same model, different frameworks can produce very different task performance. Parts of the stack that engineers once designed by hand are starting to become objects of AI-driven change.

The references in Fibona Agent sketch this research thread. Following it, progress on RSI can begin with experience accumulation—but the turn that matters most is when a system starts changing the methods that produce the next round of improvement.

Experience need not live in model weights

Early self-improvement took a pragmatic route: keep the model fixed, and first make prior experience usable.

Reflexion turns task feedback into written reflections for later attempts; Voyager, in Minecraft, saves successful behaviors as executable skills. One leaves experience; the other leaves reusable programs. Both let gains from one task influence the next. Reflexion, Voyager

As experience grows, organization becomes the bottleneck. Models can only take in a limited amount of information at once; that currently visible information is the context. ACE maintains context as a continuously updated playbook, so repeated compression into summaries does not erase detail. In 2026, MCE jointly optimizes both the context and the skills that organize it: the system accumulates experience and also revises how experience is distilled. ACE, MCE

These methods show that performance can improve without changing model parameters. They also have limits: even if the system “remembers” that it should test before submitting, an agent may still skip verification. More reliable behavior change sometimes requires editing the execution flow itself.

From writing prompts to rewriting the framework

Letting AI design workflows is not new in 2026. ADAS already represented agents as code and had another agent search for better designs; AFlow improves workflows through search and execution feedback. Both turn pipelines that once depended on hand-built scaffolding into programs that can be evaluated and iterated. ADAS, AFlow

Newer work focuses more on what evidence drives a change. Meta-Harness lets a proposer inspect historical versions of source code, scores, and full execution traces. Knowing only that something “failed” is usually not enough; whether the failure came from missed retrieval, tool misuse, or lost context has to be read from the process. Meta-Harness

Self-Harness turns that idea into a concrete loop: locate the current model’s weaknesses in the traces, propose small edits, then run regression tests to check whether existing capabilities break. The framework can then adapt to how a model actually behaves, rather than forcing every model into one hand-designed template. Self-Harness

Even here, automated design should be distinguished from recursive self-improvement. A fixed optimizer that keeps emitting new frameworks can cut human development cost without improving the optimizer itself. Recursion goes further: the program responsible for improving the system must also fall inside the scope of modification.

The improver becomes something to improve

STOP, in 2023, posed a direct experiment: write a program optimizer, then have it optimize its own code. The optimizer might not only emit better programs; it might also acquire a more effective search method. The authors were clear, though, that the underlying language model did not change—so this was not yet full RSI as they defined it. Many papers today use a broader, system-level definition; that difference matters when reading the literature. STOP

DGM combines self-modification with evolutionary search. It keeps multiple agent versions, chooses starting points among them to spawn new variants, and validates candidates with task performance. Keeping historical branches helps prevent search from collapsing too early onto whatever looks best at the moment. DGM

Hyperagents put the task-executing agent and a “meta-agent” that edits it inside the same editable program. The meta-agent can modify the task agent and itself, so how future improvements are generated is no longer fully fixed. The paper reports that some meta-level improvements transfer across domains and accumulate across runs. Hyperagents

This touches the core hope for RSI: gains from one improvement can help produce the next. But better task performance does not automatically prove better improvement ability. An agent that solves more coding problems is not necessarily better at designing agents.

AIDE² tests that distinction. A September 2026 paper reports an 8-day run that produced 99 rewrite proposals, 7 of which were accepted; gains were also checked on tasks that did not participate in selection. The evaluation controlled for budget to rule out advantages that come only from more compute. AIDE²

Researchers then placed the improved agent in the role that drives self-improvement, asking whether it was more effective than the original. That “ignition test” has not yet yielded a firm conclusion. There is evidence of continued improvement; recursive acceleration remains to be shown. AIDE²: Ignition test

Evaluation may be the hardest part

These experiments rest on a premise: the system can tell a useful change from a harmful one. On real tasks, that condition is often incomplete. Successful execution does not mean a correct result; passing the current tests does not guarantee the same edits will hold on a new batch of tasks.

TTHE tries to keep editing the framework at test time without final-answer labels. It proposes candidates from execution traces, selects among them using signals from execution, and carries the chosen framework into the next batch of tasks. The underlying model stays fixed. TTHE

That makes adaptation closer to real use—and exposes the limits of feedback. The paper finds that useful candidates were sometimes generated but not selected. A system may be able to propose good edits yet lack a reliable basis for judging why they are good. TTHE: Limitations

So when watching RSI progress, evaluation design matters as much as code-generation ability. Whether gains appear on held-out tasks, whether compute cost is controlled, and whether old capabilities regress are more persuasive than a single rising score curve. Letting an agent rewrite itself should not mean letting it rewrite the scoring rules at will.

Where this is used today

From the public materials checked for this note, what has entered products is mainly continuous adjustment of memory, skills, and workflows; modifying one’s own code in ways that raise the efficiency of self-improvement remains mostly research. The two should not be treated as equally mature.

Software development is a direct landing point. The open-source coding tool Prime Agent offers a `/refine` flow: read its own execution logs, make small adjustments to prompts, memory, skills, or sub-agent configuration, and persist them for later sessions. Official examples include saving experience from test failures as memory and callable skills. Methods discovered during development need not be rebuilt from scratch each time. Having the capability, though, is not the same as proving it steadily raises development efficiency on every project. Prime Agent

Long-running personal assistants take a similar path. Hermes Agent already ships desktop and cloud use, with cross-session memory, automatic skill generation, and scheduled reporting. Its practical role is letting an assistant keep project knowledge and working methods across ongoing collaboration. What relates to self-improvement here is the accumulation and reuse of experience; scheduled jobs and chat integrations are not RSI by themselves. Hermes Agent

Closer to RSI in the stricter sense are tools for research and algorithm development. AIDE² applies self-improved research agents to machine-learning engineering, combinatorial optimization, and scientific computing. In experiments based on WeatherBench 2, the agent optimized the numerical implementation of a physics-based weather model, testing whether research skill formed on other tasks would transfer. That is concrete application validation—but still a controlled experiment, not a claim of deployment in day-to-day operational forecasting. AIDE²

Another use is maintaining the agent itself. Self-Harness has been tried on software-repair, terminal-operation, and application-interaction benchmarks to improve patch verification, runtime control, and application-state reading automatically. For development teams, this line of work may reduce the need to inspect every failure log and hand-edit the framework; existing evidence comes mainly from benchmarks and is not yet enough to infer unsupervised maintenance of production systems. Self-Harness

What Fibona supplies is room to change

In this lineage, Fibona’s place is clearer: it mainly asks which runtime mechanisms an agent can control.

CodeAct already lets models express actions as executable code; RLM lets a model read and split long context programmatically and recursively call the model on fragments. That recursion is a way of solving tasks; it is not self-improvement by itself. CodeAct, RLM

Fibona pushes control further into generated code: the agent writes the next step and decides how to construct the next model call. A small fixed core executes and triggers repair on failure; a persistent Python session keeps state across earlier steps. Fibona Agent

This design reduces behavior that the framework must prescribe in advance—but it does not, by itself, mean the system will keep getting stronger. Self-construction addresses modifiability; sustained improvement still needs evaluation, selection, and accumulation.

Taken together, I read recent progress as agent engineering beginning to automate: organizing experience, designing workflows, and editing code are increasingly done with the system’s participation. Work such as Hyperagents and AIDE² pushes one layer deeper—whether the improvement process itself can be improved. They already offer runnable mechanisms and partial experimental results; reliable recursive acceleration still needs stronger evidence.

Suggested reading order

If you read only six papers, try ACE → Meta-Harness → DGM → Hyperagents → AIDE² → TTHE: experience accumulation, framework optimization, self-modification, meta-level modification, recursive validation, and unlabeled online adaptation. Then return to the Fibona original; it becomes easier to see which kind of architectural freedom it contributes—and which effects still need experiments to prove.
