RSI 的现实进展：AI 开始修改自己的工作方式

2026.11.04 · 约 14 分钟

English · 中文

谈到递归自我改进（RSI），人们很容易想到一种剧烈变化：AI 改进自己，变强后继续改进，最终进入能力加速增长的循环。最近几年的研究要具体得多。它们修改的往往不是大模型本身，而是围绕模型运行的代码：怎样读取资料、调用工具、保存经验，以及从失败中恢复。

这层代码通常叫 harness，也就是 Agent 的运行框架。模型相同，框架不同，完成任务的表现也可能不同。过去主要由工程师设计的部分，如今开始成为 AI 自己的修改对象。

可以把近期工作大致看成一条递进线索：先让系统用上经验，再让它改写工作流程，最后让负责改进的那部分程序也进入修改范围。真正值得关注的转折，是系统开始修改产生下一轮改进的方法。

经验不必写进模型参数

早期的自我改进有一种很务实的做法：不重新训练模型，先让它用上以前的经验。

Reflexion 把任务反馈整理成文字反思，供后续尝试参考；Voyager 在 Minecraft 中将成功行为保存为可执行技能。前者留下经验，后者留下可以复用的程序。两者都让一次任务的收获有机会影响下一次任务。Reflexion、Voyager

经验多了，如何组织它们就成为问题。模型每次能读入的信息有限，这些当下可见的信息称为上下文。ACE 将上下文作为持续更新的策略手册维护，避免反复压缩摘要时丢失细节。2026 年的 MCE 则同时优化上下文和负责整理上下文的技能：系统不仅积累经验，也调整提炼经验的方法。ACE、MCE

这类方法说明，系统可以在模型参数不变的情况下改善表现。但它们也有边界：即使记住了“提交前应当测试”，Agent 仍可能跳过验证。要更稳定地改变行为，有时需要直接修改执行流程。

从写提示，转向改框架

让 AI 设计工作流程，并不是 2026 年才出现的想法。ADAS 已经尝试用代码表示 Agent，让另一个 Agent 搜索更好的设计；AFlow 则通过搜索和执行反馈改进工作流。它们把原本依赖人工搭建的流程变成了可评估、可迭代的程序。ADAS、AFlow

近期工作更关心修改的依据。Meta-Harness 允许提案者查看历史版本的源码、得分和完整执行轨迹。只知道“失败了”通常不够；究竟是检索遗漏、工具误用，还是上下文丢失，需要从过程里判断。Meta-Harness

Self-Harness 据此形成了一个明确流程：从轨迹中找出当前模型的弱点，提出小范围修改，再做回归测试，检查是否破坏原有能力。框架由此可以围绕模型的实际行为调整，而不是要求所有模型适应同一套人工设计。Self-Harness

这里仍需区分自动设计和递归自我改进。一个固定的优化器不断产出新框架，能够减少人工开发，却未必改善优化器自身。递归更进一步：负责改进系统的那部分程序，也要进入修改范围。

改进者也成为被改进的对象

STOP 在 2023 年就提出了一个直接的实验：先写一个程序优化器，再让它优化自己的代码。优化器不仅产出更好的程序，也可能获得更有效的搜索方法。不过，作者明确说明，底层语言模型没有改变，因此这还不是他们所说的完整 RSI。如今许多论文采用的是更宽的系统层定义，阅读时需要注意这个差别。STOP

DGM 将自我修改与演化搜索结合。它保留多个 Agent 版本，从中选择起点生成新变体，再用任务表现检验。保留历史分支，可以避免搜索过早集中到眼前最好的版本上。DGM

Hyperagents 则把执行任务的 Agent 和负责修改的“元 Agent”放进同一个可编辑程序。元 Agent 既能修改任务 Agent，也能修改自己，因而后续改进的生成方式不再完全固定。论文报告，一些元层改进能够跨领域迁移、跨运行积累。Hyperagents

这触及了 RSI 的核心期待：一次改进带来的收益，可以用来帮助产生下一次改进。但任务能力提升，并不能直接证明改进能力也提升了。更会解决编程题的 Agent，未必更会设计 Agent。

AIDE² 对这一区别做了实验。2026 年 9 月的论文报告，一次持续 8 天的运行产生了 99 次改写提案，其中 7 次被接受；收益也在未参与选择的任务上接受检验。评估控制了预算，以排除单纯增加计算量带来的优势。AIDE²

随后，研究者把改进后的 Agent 放到驱动自我改进的位置，测试它是否比原先的 Agent 更有效。这项“点火测试”尚未给出确定结论。连续改进有了证据，递归加速则仍待证明。AIDE²：Ignition test

最难的部分可能是评估

上述实验依赖一个前提：系统能够识别有效改动。在真实任务中，这个条件往往不充分。程序执行成功，不代表结果正确；当前测试通过，也不能保证换一批任务仍然有效。

TTHE 尝试在没有最终答案标签的测试阶段继续修改框架。它根据执行轨迹提出候选方案，利用执行产生的信号进行选择，并将选中的框架带到下一批任务。底层模型保持不变。TTHE

这让适应过程更接近实际使用，也暴露了反馈的局限。论文发现，有用的候选有时已经生成，却没有被选中。系统可能有能力提出好改动，却缺少足够可靠的依据判断它好在哪里。TTHE：局限性

因此，观察 RSI 进展时，评估设计和代码生成能力同样重要。收益是否出现在独立任务上，是否控制了计算成本，旧能力是否退化，都比单条不断上升的分数曲线更有说服力。允许 Agent 改写自身，也不应等于允许它随意改写评分规则。

目前用在哪里

从本文核对的公开资料看，已经进入产品的主要是记忆、技能和工作流程的持续调整；修改自身代码、进而提高自我改进效率的部分，仍以研究实验为主。两者的应用成熟度不能混在一起看。

软件开发是一个直接的落点。开源编码工具 Prime Agent 提供了 `/refine` 流程：读取自身执行记录，对提示、记忆、技能或子 Agent 配置做小范围调整，并保存到后续会话。官方示例包括把测试失败的处理经验保存为记忆和可调用技能。这让开发过程中摸索出来的方法不必每次重建。不过，工具具备这套能力，不等于已经证明它能在所有项目中持续提高开发效率。Prime Agent

长期个人助手走的是相近路线。Hermes Agent 已提供桌面和云端使用方式，支持跨会话保留记忆、自动生成技能，以及定时报告等任务。其实际用途是让助手在持续合作中保留项目知识和做事方法。这里与自我改进有关的是经验的积累与复用，定时执行和连接聊天软件本身并不属于 RSI。Hermes Agent

更接近严格意义上 RSI 的应用，是改进科研和算法开发工具。AIDE² 将自我改进后的研究 Agent 用于机器学习工程、组合优化和科学计算任务。其中，基于 WeatherBench 2 的实验让 Agent 优化物理天气预测模型的数值实现，检验在其他任务中形成的研究能力能否迁移过来。这是具体的应用验证，但仍是受控实验，不应写成已经部署到日常气象预报业务。AIDE²

另一类用途是维护 Agent 本身。Self-Harness 已在软件修复、终端操作和应用交互基准中，尝试自动改善补丁验证、运行控制和应用状态读取。对开发团队而言，这条路线有望减少逐条检查失败记录、手工修改框架的工作量；现有证据主要来自基准测试，还不足以推断它能无人监督地维护生产系统。Self-Harness

可修改的运行时：把下一步写成程序

另一条与 RSI 平行、常被一起讨论的技术线，是扩大 Agent 对运行时的控制面：不只调用预设工具，而是用可执行代码表达行动，甚至自己编写下一步。

CodeAct 已经让模型用可执行代码表达行动；RLM 让模型通过程序读取和拆分长上下文，递归调用模型处理片段。这里的递归属于任务求解方式，本身不是自我改进。CodeAct、RLM

Fibona Agent 是这一方向上的一个例子：它把控制权进一步交给生成的代码，让 Agent 自己编写下一步，并决定如何构造下一次模型调用。一个小型固定核心负责执行，并在失败时触发修复；持久 Python 会话则保留前面步骤的状态。Prime Agent 等产品则把可编程运行底座与持续调整提示、记忆和技能的流程组合在一起。

这类设计减少了框架预先规定的行为，解决的是可修改性；持续改进还需要评估、选择和积累机制。它与 harness 自修改、元层 RSI 研究互补，但不应被当成整条 RSI 线索的终点或唯一入口。

综合这些研究，我更愿意把近期进展理解为 Agent 工程开始自动化：经验整理、流程设计和代码修改逐渐由系统参与完成。Hyperagents、AIDE² 等工作又把研究推向了更深的一层——改进过程本身能否被改进。它们已经给出了可运行的机制和部分实验结果；距离可靠的递归加速，还有关键证据需要补上。

推荐阅读顺序

如果只读六篇，可以依次读 ACE → Meta-Harness → DGM → Hyperagents → AIDE² → TTHE：分别理解经验积累、框架优化、自我修改、元层修改、递归验证和无标签在线适应。可编程控制面这一条线，可并行读 CodeAct 与 RLM，并可选读 Fibona 或 Prime Agent，以区分「可修改性」解决了什么、以及「持续自我改进」仍需要什么。
